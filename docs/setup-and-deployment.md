# Setup and Deployment Guide

This document describes the environment specifications, configuration variables, and operational tasks required to launch, execute, and deploy the CodeForge platform.

---

## Prerequisites & Dependencies

### Local Development Environment
To compile and execute the platform components locally, ensure the following tools are installed on your host system:
* **Java Development Kit (JDK):** Version 21 (Eclipse Temurin recommended)
* **Python Runtime:** Version 3.x (Accessible via the system path as `python3`)
* **C++ Toolchain:** GCC/G++ supporting the `-std=c++17` standard flag
* **Message Broker:** Redis Server (Running on default port `6379`)
* **Relational Database:** PostgreSQL Instance (Running on port `5432`)

---

## Environment Configuration

System behavior is driven via environment variables. Create a local configuration block or set these in your terminal environment before boot.

| Variable Name | Required Value/Format | Description |
|---|---|---|
| `PORT` | `8080` (Default) | The port where the Ktor API server binds. |
| `DATABASE_URL` | `jdbc:postgresql://<host>:<port>/<db_name>` | JDBC database connection string. |
| `DB_USER` | String | PostgreSQL authentication username. |
| `DB_PASSWORD` | String | PostgreSQL authentication credential passphrase. |
| `REDIS_HOST` | String / IP Address | Connection address for the Redis broker instance. |
| `REDIS_PORT` | `6379` (Default) | Ingestion port for the Redis engine. |
| `REDIS_PASSWORD`| String | Optional password wrapper for secure Redis environments. |

*Warning: Never commit active production credentials, tokens, or live passwords to public source repositories.*

## Local Execution Instructions

### 1. Database and Broker Infrastructure Initialization
Ensure your local PostgreSQL and Redis servers are active and listening on their respective default ports before launching the backend process.

### 2. Launching the Backend Service
The backend project handles database schema syncing, Ktor controller bindings, and background Redis worker thread initialization. Navigate to the root directory and run the Gradle application task:

```bash
# Navigate to the backend directory and execute the run task
 ./gradlew :backend:run
```
The server will boot and listen at `http://localhost:8080`. You can confirm health status by issuing a GET request to `http://localhost:8080/health`.

### 3. Launching the Compose Multiplatform Web Frontend
The client application compiles down to WebAssembly (WASM) for deployment. Execute the hot-reloading development server task:

```bash
# Execute the WASM development browser task from the root project
  .\gradlew.bat :app:webApp:jsBrowserDevelopmentRun
```
Once compilation is complete, open your browser and navigate to the local endpoint (typically `http://localhost:8081`).

## Deployment Architecture & Production Considerations

### Backend Application Hosting
The backend service can be packaged using the root-level `Dockerfile` and deployed to modern cloud hosting platforms like **Render**, **AWS ECS**, or **GCP Cloud Run**. 
* **Container Build Process:** The multi-stage `Dockerfile` leverages `eclipse-temurin:21-jdk` as a base, installs the native `python3` and `g++` compilation toolchains, and executes `./gradlew installDist` to package an optimized distribution binary.
* **Production Variables:** When deploying to platforms like Render, wire the necessary database connection strings and Upstash or cloud-hosted Redis variables directly into the cloud dashboard environment settings panel.

### Frontend Web Hosting
The production bundle generated by executing `./gradlew wasmJsBrowserDistribution` generates optimized static asset chunks (including compiled `.wasm` modules and JavaScript wrappers). These static assets can be deployed to high-performance Content Delivery Networks (CDNs) or static file hosting platforms such as **Netlify**, **Vercel**, or **AWS S3**.
